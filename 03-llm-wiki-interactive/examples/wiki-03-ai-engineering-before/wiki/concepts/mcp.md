# Model Context Protocol (MCP)

> Multiple framings — see Definition

## Definition

Every source in this wiki agrees on the mechanics: MCP is a client/server protocol (JSON-RPC over stdio or HTTP) with three native primitives — Tools, Resources, Prompts — that lets a harness call out to tools, resources and data a server exposes. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/how-to-integrate-skills-into-mcp-servers-mcp-prompts-vs]] Past that, sources genuinely disagree on what MCP *is for*, and the disagreement is worth keeping visible rather than averaged away.

**As portable delivery infrastructure.** Builder-report sources treat the MCP server as the substantial thing being built — memory, a knowledge graph, business logic — with MCP as the thin, protocol-standard shell around it: "the MCP layer is a delivery mechanism, not a logic layer." [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/agentic-graphrag-via-mcp-servers]] The same report generalizes this into a 3-layer pattern (MCP server → skills → hooks) where only the server is portable across harnesses. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/agentic-graphrag-via-mcp-servers]] [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-right-way-of-building-agents-with-mcp-servers]] echoes the same shape (memory pipeline behind an MCP server of tools + prompts) but leaves one architectural question explicitly open: whether a custom orchestrator belongs inside the server or on the client.

**As the interface to a context layer.** A related but distinct framing positions MCP not around business logic but around *your own memory*: as models and harnesses commoditize, an MCP server is what lets a portable, owned "context layer" plug into whichever harness you're using this week. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/owning-your-context-layer]]

**As one peer in a three-layer connectivity stack.** A cluster of sources explicitly reject MCP-as-the-solution: connectivity is "not one thing," and 2026 agents need skills, CLI, *and* MCP together, each covering a job the others don't — CLI for sandboxed/local/pretrained tasks, skills for reusable domain knowledge, MCP for remote access, rich semantics, and enterprise auth/governance. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]] [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/system-architecture-of-future-ai-apps-ui-tui-ide-extension]] [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-why-the-future-of-agents-is-mcp-skills]]

**As the "not dead" rebuttal.** A fourth framing engages MCP negatively, as something under attack: a viral "MCP is dead" take is read as a category error that confuses a personal single-user setup problem (where CLIs and skill files do suffice) with the professional need to govern and distribute business logic to thousands of users, which only a centrally-hosted MCP server can do. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/why-mcp-is-not-dead]]

**As the thing to avoid for local dev.** A fifth, narrower framing argues the opposite direction from a concrete anecdote: building an MCP server just to give a coding agent database access is over-engineering — a single CLAUDE.md line pointing at `mongosh`/`psql` does the job with no schema, connection handling, or context bloat. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/stop-using-mcp-servers-to-access-your-mongodb-postgres]]

## Key claims

- The raw MCP protocol (revision 2025-11-25) has no native "Skills" primitive; the word appears nowhere in its schema. FastMCP's `SkillsDirectoryProvider` packages a skill folder as MCP Resources, which by FastMCP's own description is "a packaging decision, not an architectural one" — and because Claude Code only auto-invokes MCP Tools and its own `.claude/skills/`, a skill shipped this way lands in a dead zone no client agentically calls. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/how-to-integrate-skills-into-mcp-servers-mcp-prompts-vs]]
- MCP crossed 110M monthly downloads roughly 18 months after release — pulled in by OpenAI's Agents SDK, Google's ADK, LangChain, and thousands of other frameworks, and reportedly outpacing React's adoption curve. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-why-the-future-of-agents-is-mcp-skills]]
- Good MCP servers should be task-shaped product surfaces (tools + UI + skills + tasks), not one-to-one REST wrappers; Cloudflare's server — one JavaScript-execution tool replacing roughly 80 endpoint tools — is cited as the canonical counter-example to REST-to-MCP conversion. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/system-architecture-of-future-ai-apps-ui-tui-ide-extension]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]]
- Two technical fixes recur as prerequisites for MCP working at scale: progressive tool discovery (a `tool_search` pattern that defers loading tool schemas instead of stuffing them all into context) and programmatic tool calling / "code mode" (the model writes a script against MCP's structured output instead of one inference round-trip per tool call). [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/system-architecture-of-future-ai-apps-ui-tui-ide-extension]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]]
- FastMCP (built by Prefect, not Anthropic) has become the de facto default Python SDK for both writing and connecting to MCP servers across several independent builds in this wiki, and is reported to be preferred even by MCP's own co-creator over Anthropic's official SDK. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-why-the-future-of-agents-is-mcp-skills]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/agentic-graphrag-via-mcp-servers]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/owning-your-context-layer]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-right-way-of-building-agents-with-mcp-servers]]
- MCP servers are conceded — even by a source arguing to avoid them for local dev database access — to be the right call for production guardrails and rate limiting, cross-service orchestration without CLI tools, and natural-language access for non-technical users. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/stop-using-mcp-servers-to-access-your-mongodb-postgres]]
- Siloed third-party services (e.g. Notion, Readwise) are argued to be safely reachable only through their own MCP servers, while purely local files (e.g. Obsidian) are better managed directly by a harness's CLI — MCP, CLI and skills are positioned as complementary tools for different jobs, not competitors. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/why-mcp-is-not-dead]]
- The 2026 MCP roadmap includes a stateless transport built with Google, cross-app auth via corporate IdPs, well-known-URL server discovery, v2 SDKs, and "skills over MCP" so a server can ship updated capability knowledge without a plugin/registration mechanism. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/system-architecture-of-future-ai-apps-ui-tui-ide-extension]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]]

## Tensions

**Is MCP the spine, or one peer of three?** Builder-report sources ([[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/agentic-graphrag-via-mcp-servers]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-right-way-of-building-agents-with-mcp-servers]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/how-to-integrate-skills-into-mcp-servers-mcp-prompts-vs]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/owning-your-context-layer]]) consistently center the MCP server as the primary artifact, with skills, hooks, and CLI layered on as secondary enhancements or fallbacks around it. Against that, the talk-derived sources ([[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/system-architecture-of-future-ai-apps-ui-tui-ide-extension]], [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-why-the-future-of-agents-is-mcp-skills]]) explicitly reject any single mechanism being primary: "connectivity is not one thing," and MCP, skills and CLI are co-equal layers each covering a job the others structurally can't. Neither side directly rebuts the other — it reads as a difference between how people talk about MCP in the abstract (pluralist) versus what they actually reach for first when building (MCP-centric) — but the framings do not reduce to the same claim.

> Synthesis: This wiki's three "connectivity stack" sources are not three independent witnesses to the same conclusion. [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/system-architecture-of-future-ai-apps-ui-tui-ide-extension]] and [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-why-the-future-of-agents-is-mcp-skills]] both explicitly cite David Soria Parra's "The Future of MCP" talk by name, and [[03-llm-wiki-interactive/examples/wiki-ai-engineering-after/wiki/sources/the-future-of-mcp-vs-skills]] is an unedited transcript of what is almost certainly the same talk (identical vocabulary — progressive tool discovery, programmatic tool calling, "skills over MCP," the stateless-transport-with-Google roadmap, the 110M-download figure). Treat the "connectivity is not one thing" framing and its supporting stats as one voice cited three times, not three-way corroboration — MCP is the wiki's most-mentioned concept by source count, but a genuine third-party check on the pluralist framing is still missing.
